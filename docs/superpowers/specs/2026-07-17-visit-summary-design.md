# Pulse Visit Summary (Doctor Kit v1) — Design

**Date:** 2026-07-17
**Status:** Approved by owner 2026-07-17; implementation plan pending
**Owner decisions incorporated:** v1 scoped to the current in-memory
conversation only (no Firestore/episode/profile model — see §2
non-goals); on-demand trigger, not automatic; full doctor-kit content
scope with urgency/findings/watch-for/self-care sourced deterministically
client-side rather than regenerated by the model (§5); dedicated new
Cloud Function rather than extending `assess_symptoms` (§4); shared
`_call_gemini_with_retry` extraction to keep retry/parsing plumbing DRY
across both prompts (§4.3); on-screen output only, PDF export deferred
(§9); tier-language leakage enforced in code via a response validator,
not prompt instruction alone (§4.4); the final urgency tag is the only
urgency-related value in the narrative request payload (§4.5); crisis
turns excluded from both the facts model and the narrative call, with a
fixed non-generated mention line rather than silence or a full export
ban (§6); the narrative Gemini call is user-triggered inside the screen
("Generate summary" button), not fired on screen open (§5.4).
**Post spec-review additions:** crisis stripping is defined precisely as
removing both the `type: "crisis"` assistant turn and its paired
preceding user turn, not just the tagged assistant payload (§6); `final_urgency`
is nullable on the wire with a deterministic no-Gemini-call response for
the degenerate empty-transcript case (§4.1); conversation-language
mirroring reuses `main.py`'s existing deterministic derivation rather
than prompt-only instruction, given this model's demonstrated mirroring
regression on exactly this task shape (§4.2).
**Second-pass additions:** the crisis-mention line and the tier badge
render independently, not either/or — a conversation can have both a
real assessed tier and a later crisis moment, and the doctor needs both
signals (§5.3, §6); the crisis-mention line ships as a fixed EN/TL pair
with its own narrowly-scoped selection heuristic, matching
`fallbacks.py`'s existing bilingual convention for crisis-adjacent copy
(§6); the `_call_gemini_with_retry` extraction explicitly preserves the
`_retry_used` signal `run_pipeline`'s structured logging already depends
on (§4.3); `_render_conversation_language_block`/`_CONVERSATION_LANGUAGE_COPY`
are promoted to public names since they're now shared across two prompt
modules (§4.2); a history-size ceiling, `urgencyChanged`'s derivation,
and the degenerate response's `type`/`metadata` shape are all stated
explicitly (§4.1, §5.1).

## 1. Problem

Pulse's product vision names a "doctor visit kit" — a summary of a
conversation plus doctor-facing insights — as the first fast-follow
feature after MVP (`PULSE_LAUNCH_VISION.md` v1.x roadmap;
`PULSE_TECHNICAL_PLAN.md` §6 priority #2). Nothing exists for it today:
no design, no Cloud Function, no screen. The technical plan treats an
episode data model (Firestore-backed conversation history) as a
prerequisite, but that model itself doesn't exist yet either — today the
entire conversation lives only in `ChatController`'s in-memory
`List<Message>` (`lib/features/chat/providers/chat_provider.dart`), and
nothing is persisted server-side (`functions/main.py`'s own docstring:
*"No Firestore writes this pass"*).

This design scopes a v1 that delivers real doctor-facing value now,
without waiting on that prerequisite: summarize and surface insights for
the conversation currently on screen.

## 2. Goals / Non-goals

**Goals**

1. From the current conversation, produce: a plain-language recap, the
   urgency tier and whether it changed during the conversation, findings
   noted, self-care already suggested, things flagged to monitor,
   watch-for signs, and a generated "questions to ask your doctor" list.
2. The user triggers this deliberately (AppBar action → screen → an
   explicit in-screen action for the generated part) — never automatic,
   never ambient quota spend.
3. The model's role is scoped to what only synthesis can do (the recap
   paragraph, the doctor-questions list). It never re-decides or restates
   the urgency tier — that stays deterministic, sourced from data the
   client already owns (AGENTS.md AI rule 3: the rules layer has final
   say, the AI never re-decides emergencies).
4. Crisis content is structurally prevented from reaching a printable
   document or an LLM paraphrase, while the doctor still learns a crisis
   moment occurred (§6).
5. Failure of the one networked part (the narrative call) never takes
   down the parts the user already owns (deterministic facts render
   regardless — same degraded-mode philosophy as the live pipeline).

**Non-goals (this pass)**

- Firestore persistence, the episode data model, or a profile/medication
  model — all explicitly deferred elsewhere and not prerequisites for
  this v1. This feature reads only the in-memory conversation already
  held by `chatControllerProvider`.
- Multi-conversation history, symptom timelines across episodes, or
  anything requiring profile context — none of that data exists yet.
- PDF export (`pdf` + `printing` packages). On-screen only this pass;
  export is a natural, separable follow-up once this content exists and
  is validated.
- An eval-harness category for the new prompt (§8 covers this as a
  logged follow-up, not part of this pass).

## 3. Architecture

```
ChatController's in-memory List<Message>
        │
        ├── VisitSummaryFacts.fromMessages()   [client, pure, sync]
        │     → urgency tier + progression, findings, watch-for,
        │       self-care, monitoring — all already present per-turn
        │       in each assessment's UrgencyResult. Zero network cost.
        │       Crisis turns excluded from every aggregate.
        │
        └── (user taps "Generate summary") ──▶ generate_visit_summary
              [new Callable Function, functions/main.py]
                    │
                    ├── strip crisis exchanges from history — the
                    │   type:"crisis" assistant turn AND its paired
                    │   preceding user turn (code, not prompt
                    │   instruction — §6)
                    ├── visit_summary_prompt.build_system_prompt()
                    │   [new, functions/visit_summary_prompt.py]
                    └── gemini_client.get_visit_summary()
                          [new, functions/gemini_client.py, built on
                           the shared _call_gemini_with_retry() helper
                           extracted from get_assessment() — §4.3]
                                │
                                ▼
                    { summary, questions_for_doctor, metadata }
                    validated against the schema AND the tier-language
                    blocklist (§4.4) before it ever leaves the function
```

Two independent pipelines, one screen: the facts pipeline is free,
synchronous, and always renders; the narrative pipeline is the one
deliberate, quota-costed Gemini call.

## 4. Backend

### 4.1 New Cloud Function: `generate_visit_summary`

Same deployment pattern as `assess_symptoms` — `functions/main.py`,
region `asia-southeast1`, App Check enforced via the existing
`_enforce_app_check_setting()`. A pure orchestration function
`run_visit_summary_pipeline(history, final_urgency)` sits behind the
thin Callable wrapper, mirroring `run_pipeline`/`_handle_request`'s
existing split so the orchestration logic stays unit-testable without
`https_fn` plumbing.

**Request**

- `history`: the same wire shape the client already produces via
  `Message.toHistoryJson()` for `assess_symptoms` — no new client-side
  serialization. Same rejection ceiling as `assess_symptoms`
  (`MAX_ACCEPTED_HISTORY_TURNS = 200`) applies here too — this endpoint
  is user-triggered at most once or twice per visit rather than once per
  message, so it doesn't need its own `MODEL_HISTORY_WINDOW`-style
  truncation; the full (crisis-stripped) transcript is sent to Gemini
  every time (§4.2).
- `final_urgency`: one of `wire_contract.URGENCY_TIERS`, **or `null`**.
  Null is a real, reachable state — not an error — for exactly the
  crisis-only-conversation case §5.1 and §6 already design around: when
  no non-crisis assessment ever set an urgency tier, there is no tier to
  send. Grounding only when present — see §4.5 for why this is the
  *only* urgency-adjacent value in the payload.

**Response**

```
type: "visit_summary" | "error"
summary: string
questions_for_doctor: string[]
metadata: { prompt_version, model_name, generated_at }
```

Deliberately narrow. Urgency, findings, watch-for, self-care, and
monitoring are *not* in this contract — they're already fully covered by
`VisitSummaryFacts` client-side (§5.1), sourced from data the model
would otherwise be asked to reproduce and could get subtly wrong.

**Degenerate case, resolved**: if crisis-stripping (§6) leaves `history`
empty — the conversation consisted solely of a crisis exchange, nothing
else was ever discussed — `run_visit_summary_pipeline` skips the Gemini
call entirely and returns a fixed deterministic response (`summary`: a
plain "no other symptoms were discussed" line; `questions_for_doctor:
[]`) rather than asking the model to summarize nothing. Same principle
as §6's crisis-mention line: a degenerate, safety-adjacent case gets a
fixed, non-generated answer, not an LLM improvisation. Stated explicitly
since it's otherwise easy to get wrong by analogy with `run_pipeline`'s
locally-constructed responses: `type` is still `"visit_summary"` (this
is a valid, complete result, not a failure — `"error"` stays reserved
for §4.4's actual validation-exhausted path), and `metadata.model_name`
is still populated with `gemini_client.MODEL_NAME` (identifies what
*would* have been called, for consistency with every other response's
metadata shape) even though no call was made this time.

### 4.2 New prompt module: `functions/visit_summary_prompt.py`

Separate file from `system_prompt.py`, own `PROMPT_VERSION` (starts at
`"1.0.0"` — an independent versioning track, since this prompt is a
different task with a different calibration story, not a variant of live
triage). Task: read the full transcript (post crisis-stripping, §6) and
produce a cohesive plain-language recap plus a grounded
"questions to ask your doctor" list. Same hedging discipline as
`system_prompt.py` — AGENTS.md AI rule 4 applies here exactly as it does
to live triage: never assert a diagnosis, hedged/plural language only.
Plus the new hard rule from §4.4: never state or imply an urgency tier
in its own voice.

**Language mirroring.** `gemini-3.1-flash-lite` has twice regressed on
conversation-language mirroring badly enough that live triage needed a
server-derived directive, not prompt instruction alone, to hold it
(`main.py`'s `_conversation_language`, feeding `system_prompt.py`'s
`CONVERSATION LANGUAGE` block — see `flash_lite_31_mirroring_regression`
history). `visit_summary_prompt.py` is a new, open-ended narrative
prompt over a Taglish-capable transcript — the same task shape that
triggered that regression — so it inherits the mechanism rather than
re-solving it: `run_visit_summary_pipeline` derives the conversation's
language from the crisis-stripped history the same deterministic way,
and `visit_summary_prompt.build_system_prompt` accepts a
`conversation_language` parameter and renders the same directive block.
Since this helper is now shared across two prompt modules,
`_render_conversation_language_block`/`_CONVERSATION_LANGUAGE_COPY` are
promoted to public names in `system_prompt.py` (drop the leading
underscore) rather than have `visit_summary_prompt.py` reach across a
module boundary to import a private symbol — same "second consumer
means promote, don't duplicate or reach into internals" rule already
applied to the shared widget extraction in §5.3. Left to
the implementation plan: `_conversation_language`'s current signature
takes a distinct newest `message` plus prior `history`, shaped for
live triage's per-turn call; the visit-summary call site has only a full
transcript and no separate new message, so it calls the same derivation
over that transcript's own newest user turn instead.

### 4.3 Shared retry/parsing extraction (`gemini_client.py`)

`get_assessment`'s retry-on-malformed-output loop, markdown-fence
stripping, and corrective-retry request-building are generic — not
specific to the live-triage schema. Extract into:

```python
def _call_gemini_with_retry(
    system_prompt: str,
    contents: list[types.Content],
    validator: Callable[[dict], dict],
) -> dict:
    """Calls Gemini, parses+validates the response, retries once with a
    corrective suffix on failure, raises ModelResponseError if the retry
    also fails. Shared by get_assessment and get_visit_summary — the
    retry/parsing mechanism is identical; only the schema differs.
    Sets result["_retry_used"] on the returned dict exactly as
    get_assessment does today — this is not dropped in the extraction."""
```

**Explicit carry-over, not an incidental detail**: `get_assessment`
today sets `result["_retry_used"]`, and `main.py`'s `run_pipeline`
depends on it (`retry_used = bool(model_result.pop("_retry_used",
False))`, feeding the structured-logging `retry_used` field, which has
its own dedicated regression test,
`test_logging_reports_retry_used_true_when_the_client_retried`). The
extraction must preserve this: `_call_gemini_with_retry` sets
`_retry_used` itself (both branches — the first-attempt-succeeds path
sets `False`, the retry-succeeds path sets `True`), so `get_assessment`
becomes a thin wrapper that returns the helper's result unchanged and
`run_pipeline`'s existing logging keeps working without modification.
`get_visit_summary` gets the same key on its return dict for free,
whether or not it ends up using it.

`get_assessment` becomes: build contents via the existing
`_build_contents`, call `_call_gemini_with_retry(system_prompt, contents,
_validate_payload)`. The new `get_visit_summary(system_prompt, contents)`
calls the same helper with `_validate_visit_summary_payload` (§4.4) as
its validator. This keeps the safety plumbing (never surface malformed
output, never skip the retry, never lose the retry signal) DRY across
both call sites while keeping each prompt's schema and content cleanly
separate — the same separation-of-concerns instinct already applied
between `red_flags.py` and `system_prompt.py`.

How the crisis-stripped transcript becomes `contents` for this call is
left to the implementation plan: the existing `_build_contents(history,
user_message)` is shaped around "answer this new message," not
"summarize this whole transcript with no new message," so
`get_visit_summary` likely needs a small dedicated contents builder
rather than reusing `_build_contents` as-is.

### 4.4 Tier-language enforcement — code, not prompt alone

A schema requiring `summary: string` has no opinion about what words go
in that string. Nothing about the narrow response contract in §4.1 by
itself stops the model writing "you should seek care now" inside the
recap. Enforcement is two layers, and the second is the one that
actually matters:

- **Prompt-side** (`visit_summary_prompt.py`): an explicit hard rule —
  never state or imply an urgency tier, never use tier-recommendation
  language (EN or Taglish) in its own voice; the recap describes what
  was discussed, it does not re-decide or restate what to do. Framed to
  the model as: that information is already shown elsewhere on the
  screen from a trusted source, so the recap doesn't need to carry it.
- **Code-side** (`gemini_client.py`): a `_TIER_LANGUAGE_BLOCKLIST`
  constant. **v1 ships with EN + Taglish phrases active only.** Ilocano
  entries are drafted alongside them (same Claude-drafts/
  clinician-reviews convention already established for other Ilocano
  copy in this project) but held out of the active blocklist until that
  review lands — an enforcement mechanism is exactly the wrong place to
  wire in unreviewed medical-adjacent phrasing, so "drafted" means
  written down for the reviewer, not yet checked at runtime (tracked in
  §9). `_validate_visit_summary_payload` case-insensitively scans
  `summary` and each `questions_for_doctor` entry against it. A match is
  a validation failure — same treatment as structurally malformed JSON:
  retried once via `_call_gemini_with_retry`, and if it still fails, the
  function returns `type: "error"` (never a raw leak, and never a raw
  500 — consistent with the existing Gemini-error-handling fix in
  `run_pipeline`).

This is the same enforcement-over-advisory instinct as the domain
boundary gate (`2026-07-15-domain-boundary-gate-design.md`): the rule
that matters is the one a machine checks.

### 4.5 Payload boundary, stated explicitly

`final_urgency` is the *only* urgency-related value that crosses into
the `generate_visit_summary` request. Watch-for, findings, self-care,
monitoring, and urgency progression all stay client-side per §5.1. This
line exists so a future revision doesn't casually widen the payload
("also pass watch_for for grounding") without the same scrutiny this
got.

## 5. Client

### 5.1 Deterministic facts — `lib/features/visit_summary/models/visit_summary_facts.dart`

```dart
class VisitSummaryFacts {
  final UrgencyLevel? finalUrgency;   // null if only crisis turns occurred
  final UrgencyLevel? initialUrgency;
  final bool urgencyChanged;
  final bool hadCrisisTurn;
  final List<String> findings;
  final List<String> watchFor;
  final List<String> selfCare;
  final List<String> monitoring;

  factory VisitSummaryFacts.fromMessages(List<Message> messages) { ... }
}
```

Pure, synchronous, zero network cost — walks each message's
`UrgencyResult` (`payload.type == ChatTurnType.assessment`), aggregating
`findings`/`watchFor`/`selfCare`/`monitoring` (deduped) and tracking the
first and last `urgency` seen. **Crisis turns
(`ChatTurnType.crisis`) are excluded from every aggregate** — see §6.
`finalUrgency` is nullable specifically for the crisis-only-conversation
edge case: if every assessment-shaped turn was a crisis turn, there is
no non-crisis urgency to report, and the screen must render that
gracefully (§6), not crash or show an empty badge.
`urgencyChanged` is simple first-vs-last: `initialUrgency` (the first
non-crisis assessment turn's tier) compared to `finalUrgency` (the
last) — not "did it ever fluctuate mid-conversation." A conversation
that went monitor→see-doctor-soon→monitor reports `urgencyChanged:
false`, matching the header's "started at X, now at Y" framing rather
than trying to narrate a full path.

### 5.2 LLM narrative

- `lib/features/visit_summary/models/visit_summary_result.dart` —
  `VisitSummaryResult.fromJson` (`summary`, `questionsForDoctor`,
  `metadata`), mirroring how `UrgencyResult.fromJson` already parses
  `assess_symptoms` responses defensively (never throws on a malformed
  shape).
- `lib/features/visit_summary/repositories/` — `VisitSummaryRepository`
  (abstract) + `CallableVisitSummaryRepository`, same shape as
  `ChatRepository`/`CallableChatRepository`. A `FixtureVisitSummaryRepository`
  alongside it, following the existing `_useFixturesInDebug` pattern in
  `chat_provider.dart` — the deliberate-trigger design (§5.4) means the
  facts half of this screen is already fixture-free-by-construction; a
  fixture repository extends that to the narrative half too, so the
  whole screen is demoable with zero API calls.
- `lib/features/visit_summary/providers/visit_summary_provider.dart` —
  `VisitSummaryController extends AsyncNotifier<VisitSummaryResult?>`,
  `build()` returns `null` synchronously (idle — no fetch on creation),
  with a `generate({required List<Message> messages, required
  UrgencyLevel? finalUrgency})` method mirroring `ChatController.send`'s
  guard/loading/error pattern: re-entrancy guard via `state.isLoading`,
  `AsyncValue.guard` around the repository call.

### 5.3 Screen — `lib/features/visit_summary/screens/visit_summary_screen.dart`

Top to bottom: header → narrative block → findings/watch-for/
self-care/monitoring sections (deterministic, instant, hidden when
empty — same convention `AssessmentCard` already uses).

**Header composition — the tier badge and the crisis-mention line
render independently, not either/or.** Gated separately:
`finalUrgency != null` shows the tier badge + progression line;
`hadCrisisTurn` shows the crisis-mention line (§6). These are not
mutually exclusive: the conversation engine's crisis lock is absorbing
and doesn't clear a prior card (`2026-07-13-conversation-engine-design.md`
§6/§9), so "an earlier real assessment, then a later crisis moment" is
an expected shape, not a corner case — and the doctor needs both
signals when it happens. Three reachable header states: tier badge
alone (`finalUrgency != null`, no crisis turn), crisis line alone
(crisis-only conversation, `finalUrgency == null`), or both stacked
(`finalUrgency != null && hadCrisisTurn`). The unreachable fourth
combination (neither) can't occur — the AppBar entry point (§5.4)
requires at least one assessment/crisis turn to exist before the screen
is reachable at all.

Narrative block: idle: "Generate summary" CTA; loading: skeleton;
error: inline message + "Try again", both disabled while in flight;
loaded: recap paragraph + doctor-questions list.

**Shared widget extraction, in scope because this screen needs it now**:
`AssessmentCard`'s list-row visuals (`_SelfCareRow`, `_MonitoringRow`,
`_WatchForPill` in `lib/features/chat/widgets/assessment_card.dart`) are
private to that file today. This screen is a second consumer of the same
visual language — exactly AGENTS.md's bar for promoting a shared widget
("reused across 2+ screens"). Extract to `lib/shared/widgets/`
(`checklist_row.dart`, `warning_pill.dart`); both `AssessmentCard` and
this screen consume them, keeping the two surfaces visually in lockstep
automatically rather than by convention.

### 5.4 Entry point and the deliberate-trigger decision

`chat_screen.dart` AppBar gets a new action, enabled when
`ref.watch(chatControllerProvider)` contains at least one
assessment/crisis turn. Tap → `go_router` push to `/visit-summary`,
reading `chatControllerProvider` directly (no route params — one
in-memory conversation, no ID to thread through yet).

The narrative call does **not** fire on screen open. `AsyncNotifier`
firing on `build()` would mean opening the screen costs a quota'd API
call before the user has confirmed they want it — someone curious taps
the icon, glances, backs out, and that's a burned call from a 20/day
budget for nothing. Instead: the screen opens showing the deterministic
sections instantly (§5.1, §5.3), and the narrative block carries its own
explicit "Generate summary" action that triggers
`VisitSummaryController.generate()`. This is why the AppBar entry point
is labeled "Visit summary," not "Generate visit summary" — the
navigation is free (a place to look, backed by data the user already
owns), and the in-screen button is the honest commitment point for the
paid call. A future contributor who wonders "why doesn't this auto-load,
seems like friction" should find this paragraph before removing the
button.

## 6. Crisis handling

Crisis content in a printable, shareable document — visible to a family
member or an employer, not scoped to the private chat thread — is a
decision requiring explicit sign-off, not a silent default. Handling,
locked:

- `VisitSummaryFacts.fromMessages` (§5.1) excludes crisis turns from
  every aggregate.
- `run_visit_summary_pipeline` strips crisis **exchanges** from
  `history` before building the prompt or calling `get_visit_summary` —
  in code, not left to a prompt instruction. That means both halves of
  the exchange: the assistant turn with `type == "crisis"`, *and* the
  user turn immediately preceding it — the actual statement that
  prompted the crisis reply. This pairing matters concretely:
  `Message.toHistoryJson()` (§1) only ever tags `type` on assistant
  turns — a preceding user turn is an untagged `{'role': 'user',
  'content': text}` entry, so a filter that only drops `type ==
  "crisis"` entries would leave the raw triggering statement in the
  transcript sent to Gemini, silently defeating the guarantee below. The
  rule: for every assistant turn with `type == "crisis"`, drop it and
  the user turn immediately before it by list adjacency; applied for
  every crisis-type turn in the conversation, not just the first. After
  stripping, no crisis exchange — either side of it — ever reaches the
  model, so there is no paraphrase risk in the recap.
- When any crisis turn occurred, the screen renders one **fixed,
  non-generated** line — *"This conversation included a moment of
  emotional distress — consider mentioning it to your doctor."* (EN) /
  its Taglish equivalent (TL) — rendered from a boolean
  (`VisitSummaryFacts.hadCrisisTurn`), never from model output. The one
  sentence about a person's crisis moment is the one sentence the model
  can never touch. **Ships as a fixed EN/TL pair**
  (`_CRISIS_MENTION_EN`/`_CRISIS_MENTION_TL`, Claude-drafted, same
  clinician-review convention as other crisis copy), matching
  `fallbacks.py`'s existing bilingual convention for crisis-adjacent
  strings (`CRISIS_DEGRADED_FALLBACK_EN`/`_TL`) rather than shipping
  English-only. Selection can't reuse the backend's `conversation_language`
  value (§4.2) — the header renders instantly, before the user may ever
  tap "Generate summary," so no server response exists yet to read it
  from. Instead, `VisitSummaryFacts.fromMessages` picks the TL variant
  if any user message in the conversation matches a small fixed
  Tagalog/Taglish keyword list, defaulting to English otherwise — a
  narrow heuristic scoped only to choosing between two fixed strings
  (not a language classifier, not held to the same bar as the server's
  `mirror_probes.detect_language`), fail-open to English the same way
  the server's own `_conversation_language` defaults to `None`.
- **Crisis-only-conversation edge case, resolved now**: if the *only*
  assessment-shaped turn was a crisis turn, `finalUrgency` is null and
  the header renders just the crisis-mention line with no tier badge —
  not a blank header, not a crash. `final_urgency: null` is sent to
  `generate_visit_summary` in this state (§4.1); if crisis-stripping also
  leaves the transcript otherwise empty, the backend's degenerate-case
  handling (§4.1) applies. The visit-summary screen stays reachable for
  crisis-containing conversations (the point of excluding-with-mention
  over disabling the feature entirely, §2 goal 4) — this is exactly the
  state that path has to handle.
- This gets the standing mental-health-review flag alongside the crisis
  card and crisis prompt copy — carried into the deploy-gates note for
  this feature (§9), same tracking discipline as other crisis-adjacent
  copy in this project.

## 7. Error handling

- Backend: malformed JSON *or* a tier-blocklist match → one retry via
  `_call_gemini_with_retry` → still failing → `type: "error"` (never a
  raw 500).
- Client: narrative failure (`type: "error"`, or a thrown network/App
  Check error — both rendered through the same error UI, not two) shows
  inline in the narrative block only. Deterministic sections are never
  affected by narrative absence or failure — the facts the user already
  owns are never held hostage by the model's availability, the same
  floor-reaches-the-user property the backend already guarantees,
  rendered in Flutter.
- "Generate summary" / "Try again" both disable while a request is in
  flight (double-tap/quota guard, same instinct as `chatIsSendingProvider`).

## 8. Testing

**Backend (pytest)**

- `test_visit_summary_prompt.py` (or alongside `test_gemini_client.py`):
  the tier-blocklist validator — cases that must fail (EN tier phrases,
  Taglish equivalents, mixed case/punctuation) and cases that must pass
  (a clean recap).
- A test asserting `run_visit_summary_pipeline` strips crisis
  **exchanges** — both the `type == "crisis"` assistant turn and its
  paired preceding user turn (§6) — from the payload sent to
  `get_visit_summary` **in code**: mock/spy the call and assert neither
  the crisis reply's text nor the triggering user statement's text is
  present in `contents`. Checking only for the absence of `type ==
  "crisis"` entries would pass even if the untagged preceding user turn
  leaked through, so the assertion must check the actual user
  statement's content, not just the `type` tag.
- A test for the degenerate empty-transcript case (§4.1): a
  crisis-only conversation → `run_visit_summary_pipeline` returns the
